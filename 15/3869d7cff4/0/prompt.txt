#### **Option A: Environment Variable (DISABLED_CONTENT_SOURCES)**
```python
# In content_source_factory.py or app/config.py
disabled = os.getenv("DISABLED_CONTENT_SOURCES", "").lower().split(",")
# Then filter: get_available_sources() returns [s for s in CONTENT_SOURCES if s not in disabled]
```

**Pros:**
- Simplest to implement (2-3 lines)
- Consistent with existing env var pattern (STATE_BACKUP_ENABLED, CAFFEINE_MODE)
- Affects both API signup and dispatch immediately
- No database schema changes
- Easy to toggle without redeployment (just env var change)
- Scales: can disable multiple sources at once

**Cons:**
- Global only - can't disable per environment or per scheduled job easily
- Not visible in API/dashboard
- Requires understanding env var conventions
- Example: `DISABLED_CONTENT_SOURCES="ezoe,wix"` means only stmn1 available

- Changes visible via API (could add GET /api/sources-config endpoint)

**Cons:**
- Only affects dispatch/scheduling, not signup unless you add extra logic
- Requires validation changes to enforce which sources can be used in which rules
- Dispatch rules are about WHAT to run, not WHICH sources exist
- Creates coupling between dispatch config and source availability

**Cons:**
- Requires database schema migration
- Most heavyweight solution for simple boolean flag
- Overkill if you only need global enable/disable
- Runtime changes need cache invalidation strategy
- More deployment steps

```python
ENABLED_SOURCES = ["ezoe", "wix"]  # Just comment out stmn1 to disable
```
